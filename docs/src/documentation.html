1. Summary

Colleges collect fees through several channels at once: a cash counter, bank transfers, and online payments through a gateway that sometimes answers late or not at all. The hard part is not taking the money; it is being able to say, for any student on any day, exactly what they owe, what they paid, and where each rupee went, and proving it against the bank.

Kosha is a fee ledger that does that. An accountant opens a student's statement, records a payment and sees before submitting which installments it will clear. Online payments go through a mock gateway that can succeed, fail or time out. Every successful payment gets a sequential receipt. A daily settlement file from the gateway is uploaded and matched against what was recorded, and every mismatch has a resolution with a name and a note against it. Admins can apply concessions and reverse payments; nothing is ever edited or deleted.

The three decisions that matter most

An append-only ledger. Balances are the sum of ledger entries: demand, concession, payment and reversal. Database triggers reject UPDATE and DELETE on the ledger and on payment allocations. A reversal is a new positive entry, so the history of every account can always be read back, and a reversed payment reopens its installments without deleting anything.

Money rules live in the database, in one transaction. Each money-changing operation is a single PostgreSQL function that locks the student row, checks the rules, writes the payment, events, ledger entry, allocations, receipt number and audit line together, or nothing at all. Constraints and triggers enforce the same rules even if the API is bypassed. Idempotency keys stop double submits.

Reconciliation is a first-class flow, not a report. The gateway file is parsed and validated, matched by a pure, unit-tested function into four buckets, stored as a run, and each exception is resolved through a database function that records who resolved it and why. "Mark as paid" confirms the pending payment in the same transaction.

What was built

  • Students list, and a passbook-style statement with running balance, fee-head progress, installments and payments.
  • Record payment (cash, UPI, card, bank transfer) with a live allocation preview and a visibly marked gateway simulator; check status; mark as failed; reverse; concessions.
  • Payment detail with a state track, allocations, ledger entries and audit trail; printable A5 receipts with the amount in words.
  • Reconciliation upload, the four buckets and their resolutions; a dashboard; a readable audit log; simulated roles (admin, accountant, student) enforced by the server.
  • Five AI features, each checked in code and decided by a person (section 12): Reconciliation Copilot, Ask Kosha, smart import, messages to parents (English, Kannada, Hindi), daily brief.
  • 192 unit, 13 integration, 3 end-to-end tests, 21 AI evaluations, a nine-check ledger script.

3. Assumptions

  1. Roles are simulated. A role switcher sets a cookie; the server enforces one permission matrix. Real login and per-user row-level security are out of scope for a take-home, but the permission checks sit exactly where real auth would plug in.
  2. One institution, one academic year (2026-27), INR only. This keeps the data model focused on the ledger; multi-tenancy and currencies are future work.
  3. The payment gateway is a mock. A "simulate outcome" control (succeed, fail, time out) stands in for the provider; a small table holds what the gateway "knows", so check status and settlement have something to ask.
  4. A timed-out payment usually did go through. The mock gateway reports success when asked later, which is the common real-world case; staff can still mark a pending payment as failed.
  5. Settlement is T+1. A file whose settlement dates run from D1 to D2 covers payments made from D1−1 to D2−1; only payments in that window can be "missing in settlement".
  6. Settlement amounts are gross. The file's amount is compared directly with the payment; gateway fees (MDR) are not modelled.
  7. Fee demand for the whole year is raised on 1 July, as installments per fee head per term. There is no fee-structure editor.
  8. Allocation is oldest due date first, fee-head order breaking ties (tuition, hostel, exam, library). Overpayment is kept as an advance and applied automatically when something reopens.
  9. Receipt numbers are one global sequence with the academic year as a prefix (KSH/2026-27/000123). Gaps are possible if a transaction rolls back after taking a number; this is normal for database sequences and is noted.
  10. The demo is anchored to 24 September 2026. Seed dates are fixed so gateway references and the sample settlement file always line up after a reset.
  11. Amounts above ₹10,00,000 in one payment are refused as a guard against typing errors; it is a sanity limit, not a business rule.

4. Architecture

Why this stack

  • One codebase. Next.js serves the pages, the API routes and the server-rendered read models, so types are shared from the database row to the button label.
  • Managed Postgres. Money needs real transactions, row locks, constraints, sequences and triggers. Supabase provides a Postgres with those features and nothing to operate.
  • One-click deploy. Vercel builds the repository on push; the only configuration is three environment variables, plus OPENAI_API_KEY for the AI features.

5. Data model

Why money is stored in paise

Floating-point numbers cannot represent most decimal fractions exactly: 0.1 + 0.2 is not 0.3. A fee system adds, splits and compares amounts constantly, and a one-paisa drift is a reconciliation exception. Every amount is therefore an integer number of paise: BIGINT in Postgres and a safe integer in TypeScript. Rupees appear only when formatting for display (formatINR) and parsing user input (toPaise, which rejects more than two decimals and never goes through floating point).

Why the ledger is append-only

A balance that can be edited cannot be trusted or explained. In Kosha the balance is the sum of ledger entries, each of which points at the row that caused it: a DEMAND at an installment, a CONCESSION at a concession, a PAYMENT and possibly a REVERSAL at a payment. Triggers reject UPDATE and DELETE, a check constraint forces the sign to match the type, and a unique index allows at most one entry of each type per source row, which is what makes "confirm twice" harmless. The verification script cross-checks the ledger against balances computed independently from the domain tables.

6. Payment lifecycle

Rules

  • Only SUCCESS writes the ledger, allocates and issues a receipt.
  • Cash and bank transfer go straight to SUCCESS; UPI and card pass through PENDING.
  • Time out leaves it PENDING with its gateway reference, not counted in the balance.
  • A failed attempt is kept; a retry is a new payment with a new key.
  • Reversal (admin, with reason) adds a REVERSAL entry and reopens the installments it paid.

Idempotency, locking and allocation

Idempotency. Each opening of the payment drawer creates a UUID; the column is UNIQUE and is checked after the student lock, so double clicks, retries and parallel submits yield one payment (repeats get it back with HTTP 200). A reused key with a different amount is refused.

Locking. Every money function locks the student row first, then the payment, then the reconciliation item (a fixed order avoids deadlocks), so two payments for one student cannot allocate the same rupee twice.

Allocation. After any success or reversal, unallocated money is applied to open installments, oldest due date first. "Paid" counts only allocations of payments that are currently SUCCESS, so a reversal reopens installments without deleting rows; the rest is an advance.

10. Validation and testing

Validation at every boundary

Input is validated three times with the same rules: in the form (inline messages), by zod at the route handler (422 with the field name), and in the database by the function and by CHECK constraints. Database errors carry a machine code in the Postgres HINT, which the API maps to an HTTP status and a readable message ("This payment was already reversed.").

12. AI features

Kosha has five AI features, built with OpenAI (gpt-4.1-mini) through LangChain and LangGraph. They are designed around one rule: the AI never moves money. It reads, investigates, explains and drafts; a person decides, and every decision goes through the same locked, audited database functions as the rest of the app.

The pattern every feature follows

Language models are good at reading messy situations and writing clearly, and unreliable at arithmetic, at quoting figures exactly and at following rules every time. Each feature is therefore split so that code owns the facts and the rules, and the model owns the judgement and the words. Then code checks the model's work before anyone sees it.

ControlHow it is enforced
No money moves without a personTools are read-only queries. Accepting a Copilot suggestion runs decide_ai_investigation(), which calls resolve_recon_item() in the same transaction; escalations cannot be accepted at all.
Every figure is realA shared checker extracts every ₹ amount from the model's text and table cells; each must be one a tool returned (or the user typed). Totals, differences, percentages and date ranges are computed in code, not by the model.
Every claim has a sourceTools register evidence ids (gateway:MGW…, student:CSE24-001, check:duplicates); findings, table rows and sources must cite ids that exist, and the UI turns them into links.
Rules the model must followAllowed actions per bucket and payment status; a possible duplicate payment must be disclosed; actions in the brief must belong to their signal; messages must be in the chosen script, use ₹ digits and assume no gender.
Least data to OpenAISmart import sends only the header and at most 25 sample rows. Messages send the facts for one student. The key never reaches the browser bundle (checked after every build).
AuditableInvestigations, accept and dismiss decisions, drafted messages and briefs are stored or written to the audit log with who, when and which model.
Works without AIWith no OPENAI_API_KEY the AI buttons are hidden, and the daily brief is written by rules. Nothing else changes.

12.1 Reconciliation Copilot

Problem. A reconciliation run leaves exceptions: amounts that differ, money the gateway settled that is still pending here, payments recorded here but missing from the file. Each one takes an accountant several screens and a judgement call.

What it does. Investigate on an exception, or Investigate all for the run, streams the agent's steps live ("Asking the gateway about MGW7300000005", "Checking for a second payment of the same amount") and ends with a diagnosis: a headline, the root cause, a confidence, numbered findings linked to their records, the suggested action with an editable note, and for shortfalls a ready message to the gateway's support desk.

12.2 Ask Kosha

Problem. Questions like "who in second-year B.Com owes more than ₹50,000?" or "how did UPI collections compare with last week?" today need filters, exports and a spreadsheet.

What it does. A chat panel on every page. The answer leads with the number, shows a table whose rows open the student or payment, lists its sources, suggests follow-ups, and says how many figures were checked. The conversation carries over, so "only the BCA ones" or "how much do they owe in total?" work.

Design decisions

  • Typed tools, not text-to-SQL. The model fills validated parameters (course, status, minimum amount, date range, grouping); it can only read what these six functions return and can never write.
  • Arithmetic and dates in code. Tools return totals for all matches, per-group comparisons and percentage changes. "Last week" is resolved in code (Monday to Sunday) and the exact ranges are given to the model, after the same question once gave two different weeks.
  • Ties are never cut. "Who owes the most?" lists all three students on ₹1,73,000.
  • Stateless follow-ups. The browser sends the recent turns (including the previous table) with each question, so it works on serverless hosting without a session store.
  • Read-only and on topic. "Record a cash payment…" is refused with a pointer to the right screen; questions unrelated to the fees are declined.

Code: lib/ai/ask/ (tools, graph, periods, schema, verify, prompts), route app/api/ai/ask, components/ai/ask-kosha.tsx.

12.3 Smart settlement import

Problem. Real settlement reports never use Kosha's four column names. They have "Txn Reference", gross, MDR, GST and net amounts, a payout UTR, a transaction date next to the settlement date, and DD/MM/YYYY 12-hour times. Retyping headers is slow and error-prone, and choosing the net amount would turn every card payment into a mismatch.

  • Traps it has to avoid in the sample: Net vs Gross amount, Txn Date vs Settlement Date, Settlement UTR vs Txn Reference. The eval requires all three right.
  • Every status value is seen. Sampling includes at least one row per distinct value of each category-like column, and the preview lists every status in the whole file; reconciling is blocked until each one is mapped.
  • Day/month ambiguity. If no date has a day above 12, DD/MM and MM/DD both convert every row with different dates, so the preview requires the accountant to confirm the format.
  • Remembered layouts. A confirmed mapping can be saved for files with the same columns, and the run page records which mapping was used and who confirmed it.

Code: lib/domain/settlement-mapping.ts (converter, pure and unit tested), lib/ai/settlement-mapper.ts (graph), route app/api/ai/settlement-mapping, components/reconciliation/smart-import.tsx. Sample: public/samples/gateway_report_sep_2026.csv.

12.4 Messages to parents

Problem. Reminders and overdue notices are typed by hand, often in the parent's language, and a wrong amount in a fee message damages trust.

  • Four purposes, available only when they apply: upcoming due, overdue notice (no penalties or threats; the college charges no late fees), balance explained, payment received (with the receipt number and what it paid for).
  • Kannada and Hindi in natural, everyday language, always with an English version so staff who do not read the script can check what it says.
  • No assumed gender. The first drafts wrote "your daughter" and "आपके पुत्र" from the names alone; Kosha does not record gender, so the prompt forbids it and a check fails any draft with gendered words in any of the three languages.
  • Amounts must be checkable: written with ₹ and 0-9 digits, never in words or native digits.

Code: lib/ai/parent-message/ (facts, draft graph, verify), route app/api/ai/parent-message, supabase/migrations/005_ai_messages.sql, components/ai/parent-message-drawer.tsx.

12.5 Daily finance brief

Problem. The dashboard shows everything; an accountant arriving in the morning needs to know what to do first.

  • Signals are counted once. The same exception in two runs of the same file counts once; the link goes to the newest run.
  • It knows when it is out of date. A fingerprint of the signals is compared on every dashboard load; after a payment the card says "The ledger has changed since this was written" and highlights Refresh.
  • Calm tone. Early briefs said "to secure ₹8,81,000" and "significant revenue loss"; the prompt now asks for plain, calm wording, and the eval's quiet day checks that no urgency is invented.

Code: lib/ai/brief/ (signals, brief graph), lib/data/brief.ts, route app/api/ai/brief, supabase/migrations/006_ai_brief.sql, components/ai/daily-brief.tsx.

12.6 How the AI features are tested

Two layers. Unit tests cover every deterministic part (verifiers, date periods, the settlement converter, the signal detectors), including the failure cases the verifiers exist to catch: a made-up amount, an unknown evidence id, a forbidden action, an undisclosed duplicate, an amount written in words or Kannada digits, a gendered word in Hindi. Evaluations (npm run eval:ai) run the real model on cases whose right answer is known, with the answer computed independently from the database, not by the feature's own tools.

13. Limitations and future work

Out of scope by design

  • A real payment gateway (webhooks with signature checks, status polling, settlement file download).
  • Real authentication and per-user row-level security, replacing the role cookie; per-student access for parents.
  • Late fees and interest on overdue installments.
  • A fee-structure editor: fee heads, amounts and due dates per course and term.
  • Multiple institutions (tenancy) and multiple academic years side by side.
  • Email and SMS: receipts, reminders before due dates, notices of reversals.
  • Partial refunds; today a payment can only be reversed in full.

Known limitations

  • Anyone with the demo link can switch to Admin and reset the data. Acceptable for a demo; the first thing real auth removes.
  • Reconciliation loads all gateway payments into memory for matching, fine for thousands of rows; at scale the window filter should move into SQL.
  • Settlement fees (MDR) are not modelled, so a real gateway's net settlements would all show as mismatches until fees are added as a column.
  • A settled-but-pending item that is later confirmed through check status stays open until someone resolves it (resolving it then records "already confirmed").
  • Receipt numbers come from a sequence and can have gaps after a rolled-back transaction.
  • A receipt lists the installments its payment pays today; if an advance is applied later, an old receipt gains a line. A receipt snapshot table would freeze it.
  • The dashboard is computed per request; a materialised daily summary would be needed for many thousands of students.

AI limitations

  • The verifiers catch invented figures and references, not a wrong interpretation with real figures (a wrong filter, a misread question). The evaluations cover the known cases; a larger evaluation set, run on every change to a prompt or model, is the next step.
  • The model's answers can vary slightly between runs even at temperature 0; decisions that matter always pass through a person.
  • Features depend on OpenAI being reachable. Without it, the buttons are hidden and the daily brief falls back to rules.
  • Sample rows sent for smart import can include payer names. A deployment would need a data-processing agreement with the provider, or an option to mask names before sending.
  • Kannada and Hindi drafts are checked for script, figures and gender, not fluency, and the one-investigation-per-item guard is in server memory (several servers would need it in the database).
